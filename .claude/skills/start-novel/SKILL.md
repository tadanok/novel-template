# 新作の構想と正典の初期化

補足： $ARGUMENTS

## 0. 前提を確かめる

- `chapters/` に章ファイルがなく、`log/continuity.md` に章の記録がないことを確かめる。
  すでに書き始めている場合は、このスキルを使わずにユーザーへ確認する。
- 次を読む：`CLAUDE.md`、`README.md`、`docs/canon-format.md`、`docs/templates/novel_design.md`、`.claude/rules/style-base.md`、
  `docs/style-presets/` の全ファイル、`novel.config.json`、`bible/`・`plot/` のひな形。

## 1. 構想の対話

ユーザーがすでに決めていることを先に聞き取り、決まっていないことを選択肢と推奨つきで尋ねる。
質問は AskUserQuestion を使い、関連するものを 1 回に最大 4 問までまとめる。決まらないものは無理に決めず、
`plot/open_questions.md` に残す。次の順で固める。

1. ジャンルと読み味（`docs/style-presets/` の見本に近いものがあるか）
2. 題材と舞台、作中の時代、実在の地名や制度をどこまで使うか
3. 主人公と主要人物（役割、関係、秘密）。題名（仮題）との関係：題名が主人公の名前を含むなら、主人公が第 1 章のうちに登場し、物語の選択を担うか
4. 視点（一人称か三人称か、視点人物の数）
5. 物語の基本構造と結末の方向。真相（物語の核となる出来事）と、その時系列
6. 主題（誰を断罪しないか、何を問い続けるか）
7. 規模（章数、目標字数）と章ごとの役割
8. 主要モチーフと伏線の大筋
9. 公開の予定（note で連載するか、全章を書き終えてから始めるか、予約の曜日と時刻）
10. 著者名（ペンネーム）。私家版の表紙と書誌情報に使う

対話の途中で、既存作品の筋・人物・トリックに似すぎている案が出たら指摘する。

## 2. 初稿の設計書を作り、承認を取る

物語の核 (真相と時系列) を初稿の途中で決め直すと、書き終えた章の書き直しが生じる。そのため、核は初稿の前に固める。

1. `docs/templates/novel_design.md` を `docs/design/novel_design.md` に写し、`{{作品名}}` を仮題に置き換える。
2. 対話の結果から、各節を埋める。特に「題名と主人公」「真相」「中心となる出来事の時系列」「情報開示の基準線」を空にしない。
   決まらないものは `plot/open_questions.md` に移し、設計書には「未確定（open_questions へ）」と書く。
3. 設計書をユーザーに示し、節ごとに承認を取る。承認日を書く。
4. 承認が取れるまで、第 1 章には進まない（未確定のまま進める項目は、承認の節に名前を書く）。

## 3. 正典を書く

`docs/canon-format.md` の書式に従い、確定した事項だけを書く。記入例の固有名詞を持ち込まない。

- `bible/theme.md`：方向性、主題、物語の基本構造、題名（仮題）
- `bible/characters.md`：呼称の統一、人物
- `bible/world.md`：舞台、過去の出来事、主要モチーフ、作中の制度・業務の運用
- `bible/timeline.md`：基準、過去の時点の年齢（あれば）。「作中の進行」は空のまま
- `plot/outline.md`：構成の表（章・目安・視点・役割）、分量の方針。「進捗」は空のまま
- `plot/foreshadowing.md`：大筋の伏線（設置章と回収章を決めたものだけ）
- `plot/open_questions.md`：決まらなかった事項と、いつまでに決める必要があるか

承認した設計書の内容を、ここで正典に移す（時系列は `bible/timeline.md`、章の役割は `plot/outline.md`、伏線は `plot/foreshadowing.md`）。
設計書と正典が食い違わないよう、移したあとで照らし合わせる。

各ファイルのひな形にある `<!-- -->` の説明コメントは、書き終えた見出しから消す。

## 4. 文体ルールを書く

`.claude/rules/style-genre.md` を、近い見本（`docs/style-presets/`）を写して作品に合わせて直すか、新しく書く。
「この作品の表記」に、固有名詞の表記、英字や記号の扱い、時刻・年齢・金額の書き方を書く。
`style-base.md` は変えない（土台を変えたいときは、ユーザーに確認したうえで雛形側も直すよう提案する）。

新しいジャンルの見本を作った場合は、作品固有の表記を除いて `docs/style-presets/` にも残すか、ユーザーに確認する。

## 5. 設定と README

- `novel.config.json`：`title`（仮題）、`author`、`episode_label`、`note.publish_schedule`、`note.start_after_all_chapters` を書く。
  `author` は対話で聞いた著者名を書く。git の設定や GitHub のアカウント名から推測して埋めない。決まらなければ空のままにし、`plot/open_questions.md` に残す。
  `viewer` と、`note` の URL は空のままにする（最初の公開や note の準備のときに埋まる）。
- `README.md`：`<!-- novel-intro:start -->` と `<!-- novel-intro:end -->` の間を、作品の紹介に書き換える。
  題名（仮題）、ジャンル、規模、公開の予定を数行で。結末や真相は書かない。
  「新作を始める手順」の節は、新作のリポジトリでは役目を終えるので、「この環境の使い方」と見出しを変え、手順 1〜3 を削る。
  直上の Mermaid の図からも A〜C のノードと、それにつながる矢印を消し、図と本文の番号を 1 から振り直す。
- `LICENSE`：雛形の MIT のライセンスが、そのまま写ってきている。このままだと原稿まで MIT で提供しているように読めるので、`git mv LICENSE docs/template-LICENSE` で移す。
  README の「ライセンスと免責」の節は、次の内容に書き換える：雛形から写した部品 (スキル、エージェント、ツール、文書のひな形) は MIT (`docs/template-LICENSE`)、原稿と正典などこの作品の文章の権利は作者にある。
  原稿にライセンスを付けるかどうか (付けないなら「無断転載を禁じます」などの一文を入れるか) は、ユーザーに確認する。決まらなければ、権利が作者にあることだけを書く。
  ディレクトリ構成の図の `LICENSE` の行も、`docs/template-LICENSE` に直す。

## 6. 確認と commit

1. 正典に書いた内容の要点（主題、主人公、章構成の表、未確定事項）をユーザーに示し、確認を取る。
2. まとめて 1 つのコミットにして push する。

## 7. 報告

- 初期化したファイル（設計書を含む）と、未確定事項の一覧
- 第 1 章を書く前に決める必要があるもの
- 第 1 章のセッションの依頼文（`docs/prompts/chapter-session.md` の「章の執筆のセッション」を埋めたもの）
